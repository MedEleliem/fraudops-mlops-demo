Le point de départ

Un projet ML solide ne suffit pas toujours à convaincre un client final.

L’ancien repository contenait déjà une base sérieuse: pipeline de préparation, resampling, entraînement, tests, DVC et logique CI/CD. La donnée actuelle reste une donnée publique de démonstration: le dataset Kaggle credit card fraud, stocké hors Git via un remote DVC Google Drive. La nouvelle étape a été de rendre ce travail lisible comme un produit: deux environnements, une gouvernance des paramètres, un registre de versions et une interface de scoring utilisable.

Du changement à la production

Chaque décision laisse une trace.

01

Configurer

Le data scientist ajuste le seuil, la stratégie de resampling ou les paramètres de sélection.

02

Tester

La candidate vit d’abord dans un environnement de test, séparé du service client.

03

Versionner

Paramètres, métriques, artefacts et notes de validation restent attachés à une version précise.

04

Comparer

La candidate est comparée à la production avant toute promotion.

05

Promouvoir

Seule une version validée rejoint l’environnement de production utilisé par le client final.

Une lecture orientée risque

Les métriques parlent ensemble.

Une accuracy élevée peut masquer un modèle inutile sur une classe rare. La décision s’appuie donc sur le recall, la précision et le F1 de la fraude.

Déploiement réel

Le notebook devient une chaîne exploitable par une équipe data.

Dans une architecture cible, FraudOps peut s’appuyer sur un serveur big data, un datamart fraude, Airflow pour l’orchestration et un feature store pour garantir que les variables utilisées en entraînement sont les mêmes que celles utilisées en serving.

Data platformIngestion et datamart

La démo s’appuie sur un dataset public stocké via DVC/Google Drive. En production, les transactions arrivent depuis un data lake, un warehouse ou un flux batch/streaming. Les transformations construisent un datamart fraude stable, auditable et réutilisable.

OrchestrationAirflow et CI/CD

Airflow orchestre l’ingestion, les contrôles qualité, le calcul des features, le retraining et les validations. GitHub Actions garde la partie code, tests et packaging sous contrôle.

Model storePlusieurs modèles, un seul cadre

Régression logistique, random forest, gradient boosting ou modèles spécialisés peuvent coexister dans le registry. Chaque version garde ses paramètres, métriques, artefacts et seuil de décision.

End clientServing contrôlé

Le client final interroge uniquement l’API de production. L’équipe data peut manipuler, tester et comparer les modèles sans casser le service consommé par le métier.
